# 백엔드·연결 프로그램 수정 확인

기능 검토 F03~F07과 일정·미리보기 복구 API를 수정했다. 기존 소유 파일 **8개 중 8개**를 확인하고 수정했다. F01의 원본 실행 관측을 추가했으며, F01·F02의 화면 판정과 F08의 최신순 정렬은 프런트엔드 작업 범위다.

- 스냅샷: 메타데이터와 자산 청크를 한 SELECT로 읽는다. 자산 청크가 누락되면 정상 빈 재고 대신 503을 반환한다. D1 행 크기 제한을 위해 청크를 한 행으로 합치지 않는다.
- 일정: 모든 활성 일정과 최근 완료·취소 100건을 제공한다. 과거 이력은 커서로 조회한다. 실패 원인과 계정·제목·종류를 보존하고 실패 일정 취소 및 새 예약을 지원한다.
- 지시: 같은 ID의 재전송을 연결 상태·큐 상한보다 먼저 처리한다. 같은 동작·대상의 대기 지시는 원자적 INSERT 조건으로 합친다.
- 미리보기: 파일 없음·읽기 실패를 회신한다. 60초·300초 지연 후 최대 3회 시도하며, 이후 화면에 실패 ID를 제공하고 명시적 재시도로 복구한다. 앞의 실패 파일 때문에 뒤의 정상 파일이 막히지 않는다. 48건 실패 회신은 49쿼리, 25건 성공 회신은 27쿼리다.
- 로컬 SQLite: 동기 트랜잭션 중 이벤트 루프에 양보하지 않아 동시 batch가 겹치지 않는다. 개발 API도 같은 어댑터를 사용한다.
- 업로더: 원본 상태 파일 수정 시각, 실행 잠금 활성 여부, 원본 launchd 순회 주기 60초를 수집한다. 상태 파일과 잠금 파일을 새로 만들거나 고쳐 쓰지 않는다.

검증 결과는 **Node 33/33, Python 8/8 통과**, 실패·건너뜀 0이다. 모든 쓰기는 메모리 DB·임시 원본에서 수행했다. 운영 원본 쓰기, 실제 지시, 실제 일정 생성은 0회다.

회귀에는 과거 이력 350건과 활성 일정 311건의 공존, Unicode 이력 커서의 누락·중복 방지, 읽기 도중 신규 스냅샷 게시, 청크 누락, 앞 48건 미리보기 실패, 동시 batch 100개 중 의도적 1개 실패의 독립 rollback, 동시 지시 16건의 단일 접수를 포함한다.

새 스키마는 `preview_failures`·`command_requests` 테이블과 대기 지시 검색용 부분 인덱스를 `IF NOT EXISTS`로 추가한다. 임시 DB에서 중복 적용 → `DROP TABLE command_requests; DROP TABLE preview_failures; DROP INDEX commands_queued_payload; DROP INDEX commands_history;` → 재적용을 확인했고 기존 일정은 보존됐다. 이 되돌리기는 실패 미리보기 이력과 합쳐 접수한 요청 ID의 연결 기록을 지운다. 재전송 안전성을 유지해야 하는 운영 중에는 요청 연결 기록을 지우면 안 된다. 운영 DB에는 실행하지 않았다.

성능 관측은 Node v26·메모리 SQLite에서 인증과 JSON 직렬화·파싱까지 포함했다. 13계정·9천 자산·활성 일정 310건·과거 350건으로 동시 4개, 총 100회 읽기를 측정했다. **p95 196.46ms, p50 113.54ms**, 자산 1개와 9천 개 모두 9쿼리로 N+1은 0이다. 실험 목표 150ms는 초과했으며 프로젝트의 확정 지연 예산은 없다. Cloudflare·HTTP 네트워크 성능은 이 수치로 판단할 수 없다. 실행 계획에서 기존 `schedules_due`와 새 `commands_queued_payload`·`commands_history` 인덱스 사용을 확인했다.

증거: `artifacts/repair-backend/node-tests.txt`, `python-tests.txt`, `performance.json`. 명령: `npm test`, `python3 tests/bridge_test.py`, `node tests/backend-benchmark.mjs`.

활성 일정은 누락을 막기 위해 전부 반환한다. 수만 건 규모의 활성 일정이 실제로 생기면 활성 목록에도 서버 페이지네이션을 추가해야 한다. 물리 업로더 중단 주입, Cloudflare 실환경 부하, 프런트엔드 표시·조작은 이번 백엔드 확인에 포함하지 않았다.

독립 재심의 잔여 3건도 수정했다. 청크가 파손돼 503인 상태에서 정상 새 스냅샷을 받으면 200으로 복구하며 과거 게시 거부는 유지한다. 합쳐 접수한 요청 B는 `command_requests`에 원본 지시 A와 연결해 보존하므로 A 완료 뒤 B 재전송도 A의 완료 결과를 반환하고 새 지시를 만들지 않는다. 동시 요청 16개의 연결 기록과 완료 후 재전송도 확인했다. 실제 로그인 세션으로 미리보기 24건을 명시 재시도하면 총 28쿼리이며, 50쿼리 초과 시 오류를 던지는 격리 모형에서도 202를 반환한다.

대기 지시의 가시성도 보완했다. `/api/world`는 한 SELECT에서 대기 지시 전부와 최근 종료 지시 40건을 합쳐 반환한다. 오래된 대기 지시 200건·새 종료 지시 41건에서 대기 200건/종료 40건/중복 0건과 재조회 시 동일 정렬을 확인했다. 종료 이력 조회의 부분 인덱스를 추가했고 실제 실행 계획에서 사용을 확인했다.
