# 심사와 다음 행동의 데이터 계약

2026-10-23. 첫 화면의 정본은 `src/owner-cycle.ts`다. 계정의 현재 심사와 다음 제출·확인은 서로 다른 정보이며 동시에 표시한다.

| 정보 | 근거 | 화면에서 말할 수 있는 것 |
|---|---|---|
| 현재 심사 중 | 계정별 현재 고유 제작물의 `state=submitted` | `심사 20`, `심사 비었음`. 과거 제출 횟수를 더하지 않는다. |
| 플랫폼 대기 수 | `capacity.pending`, `capacity.observed_at` | 추적 중인 제작물과 다르면 `심사 수 대조`. 어느 쪽도 조용히 덮어쓰지 않는다. |
| 심사 예상일 | 현재 심사가 있을 때의 `reviewOn` | 예상일이다. 현재 심사가 없으면 과거 제출분의 날짜를 숨긴다. 기한 경과는 승인·완료가 아니다. |
| 다음 계정 확인 | `nextCheckAt` | 정상 계정은 `확인`, 문제가 있는 계정은 `재시도`와 날짜·시각. 제출 시각으로 표시하지 않는다. |
| 다음 제출 계획 | 가장 최근 제출 달력의 `next_upload_on` | 사람이 기록한 `제출 계획`. 실행 예약이 아니다. 새 제출분에 계획이 없으면 이전 날짜를 상속하지 않는다. |
| 제출 실행 예약 | 연결된 작업 ID·수락 결과가 필요 | 현재 API와 연결기에 이 기능은 없어 `null`. 예약을 추정하거나 날짜를 만들어 내지 않는다. |
| 재확인 요청 예약 | 관제 `schedules.kind=recheck` | 해당 시각에 계정 재확인을 요청한다. 플랫폼에서 그 시각에 조회·제출을 마친다는 뜻이 아니다. |
| 전체 순회 가능 시각 | `automation.nextAt` | 전체 작업기의 간격 조건. 특정 계정의 제출 예약으로 쓰지 않는다. |

전경의 심사·상태·다음 확인과 수동 제출 계획은 별도 축이다. 계획이 있어도 구체적인 실패 원인은 유지하며, 실행 중이거나 자동화가 정지돼도 기록된 계획을 지우지 않는다. 계획은 실행 예약이 아니라는 안내를 계정 행동판과 일정에 남긴다.

실제 자료를 읽은 2026-10-23 20:04 한국 시간에는 심사 220개, 빈 심사 1·13번, 제출 계획·관제 예약 0건이었다. 빈 두 계정도 제작물은 있으나 계정 확인이 막혀 있었다. 따라서 재고가 많다는 표시보다 `심사 비었음 · 제출 막힘 · 재시도 시각`이 우선이다. 이 수량은 당시 기록이며 제품에는 최신 관측을 표시한다.

심사 중인 그림이 있으면 결과 확인 후 다음 제출을 판단한다. 심사는 없고 승인 작품만 남아 있으면 공개 상태 확인을 기다릴 수 있다. 둘 다 없고 재고가 있으면 자동 순회에서 계정·한도를 확인한 뒤 제출할 수 있지만, 확정 시각은 없다. 자동화가 정지되거나 관측이 끊기면 미래 동작을 정상 예약처럼 약속하지 않는다.

현재 설치된 연결기는 재확인 대상을 원본 `scan.pending`에 넣는다. 원본 작업의 잠금이 유지되면 요청을 대기 상태로 남기고 기존 간격·계정 순서를 따른다. `applied`는 대기열 반영이며 실제 플랫폼 조회·제출 완료는 후속 관측으로 판단한다. 이 조사 중 다른 작업에서 연결기 소스와 설치본이 갱신된 것을 읽기 전용으로 확인했으며, 이번 화면 작업에서 원본 자동화나 연결기를 수정하지 않았다.

정상·문제 계정, 심사 0/20, 계획·확인 요청·미예약, 공개 대기, 관측 끊김, 과거 날짜와 서로 다른 심사 수를 단위 시험한다. 실제 운영 데이터를 바꾸는 시험은 하지 않는다.
