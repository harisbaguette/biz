# UI·시각·반응형 독립 심사

**판정: 반려.** 3D 단지와 데이터 연결은 확인되지만, 현재 화면은 업무를 공간에서 읽는 경영 게임보다 번호로 여는 3D 목록에 가깝다. 핵심 조작의 잘림, 계정 누락, 작은 화면의 마커 밀도 때문에 요청한 상용 수준으로 판정할 수 없다. 이 평가는 저폴리 스타일이나 무료 에셋 자체에 대한 반려가 아니다.

지정 캡처 **13개 중 13개**를 직접 열었다. 6개 화면 크기의 전체·계정 화면 12개와 Cloudflare 실행 화면 1개다. 현행 빌드의 두 배치 결함은 게임 심사자의 새 headless 재현 기록으로 교차 확인했다. 소스 수정은 하지 않았다.

| 우선순위 | 발견 수 | 의미 |
|---|---:|---|
| P0 | 0 | 데이터 손실·완전 차단을 확인하지 않음 |
| P1 | 5 | 초기 관제와 상태 판단을 방해 |
| P2 | 4 | 가독성·조작·시각 완성도 미달 |
| P3 | 0 | 별도 취향 지적은 추가하지 않음 |

## UI-01 · P1 · 가로 모바일에서 첫 화면의 주 메뉴가 잘린다

**관측.** 844×390의 `landscape-mobile-world.png`에서 하단 dock가 거의 화면 아래에 있다. 현행 빌드의 별도 재현도 dock `y=373, height=57`, 하단 430px로 **40px가 viewport 밖**임을 확인했다. 계정 선택 후 캡처에서는 페이지가 이동해 보이므로, 이후 화면만 확인하면 놓친다.

- 영향: 처음 열었을 때 재고·일정·오류·운영 메뉴의 이름과 조작부가 감춰진다. 지원 화면 방향에서 핵심 관제가 시작되지 않는다.
- 근거: `src/style.css:93`의 `height:100dvh; min-height:440px`가 높이 390px보다 큰 루트를 강제한다. `src/style.css:2159`의 dock 하단 위치는 그 루트를 기준으로 한다.
- 최소 개선: 높이가 작은 가로 화면에서 루트 최소 높이를 해제하고 실제 viewport 안에 dock를 고정한다. 강제 페이지 스크롤로 복구하지 않는다.
- 합격: 844×390과 740×360에서 새로 연 직후, 스크롤 없이 5개 목적지와 주 조작 전체가 viewport 안에 있고 각 메뉴를 누를 수 있다.
- 증거: `artifacts/verification/landscape-mobile-world.png`, `artifacts/review-2026-10-18/game/landscape-mobile-initial.png`, `game/initial-observations.json`.

## UI-02 · P1 · 세로 PC의 전체 단지 보기에 13개 계정이 들어오지 않는다

**관측.** 900×1440 초기 화면에서 09번이 왼쪽 프레임 밖이다. 새 headless 재현의 09번 마커는 `x=-56.45, width=51.78`로 완전히 벗어났으며 CSS `visibility=visible` 상태다. 제목은 13개 작업동인데 실제 한 화면의 선택 대상은 12개다.

- 영향: 사용자는 09번의 정상·이상 여부를 첫 화면에서 확인할 수 없고, 이동해야 한다는 사실도 알기 어렵다.
- 근거: `src/world/World.tsx:590`은 너비 세 구간으로 정사영 카메라 span을 정하며, 가로세로비·실제 단지 경계·HUD 안전 영역을 함께 맞추지 않는다. `World.tsx:289`의 전체 단지 보기 역시 고정 zoom=1이다.
- 최소 개선: 실제 단지 bounding box를 화면의 사용 가능 사각형에 맞추고, 전체 보기·회전·resize 후에도 그 맞춤을 유지한다. 패널이 열리면 선택한 시설을 남은 영역 중심으로 옮긴다.
- 합격: 360×740, 390×844, 768×1024, 900×1440, 1440×900, 844×390의 초기·전체 보기에서 13개 대상이 모두 읽히고 선택된다.
- 증거: `artifacts/verification/portrait-pc-world.png`, `artifacts/review-2026-10-18/game/portrait-pc-initial.png`, `game/initial-observations.json`.

## UI-03 · P1 · 모바일에서 건물보다 번호판이 장면을 지배한다

**관측.** 360px·390px 전체 화면에서는 불투명한 번호판이 건물의 전면과 도로를 덮는다. 844×390에서는 13개의 판이 서로 겹친다. 데스크톱에서도 모든 시설에 동일한 판을 상시 배치한다.

- 영향에 대한 추론: 사용자는 시설의 위치·상태를 공간으로 익히기보다 번호와 팝업을 반복해서 읽게 된다. 특히 작은 화면은 화면의 가장 큰 재료인 3D 건물이 번호판의 배경으로 내려간다. 실제 오탭률은 측정하지 않았다.
- 근거: `src/world/World.tsx:555`는 투영 위치만 정하고 마커 사이의 충돌·밀도·HUD 가림을 처리하지 않는다. `src/style.css:210`, `:2081`에서 판 크기는 지도 축척과 독립적이다.
- 최소 개선: 정상 대상은 작은 번호 표식으로, 문제·선택 대상은 읽기 쉬운 판으로 승격한다. 축척에 따라 식별 정보 수준을 바꾸고 충돌 시 위치를 정리한다. 터치 영역은 44px 이상으로 유지하되 서로 겹치는 투명 영역을 만들지 않는다. 전 대상을 작은 아이콘으로만 축소하는 처방은 피한다.
- 합격: 위 6개 크기에서 같은 계정의 표식과 건물이 혼동되지 않으며 마커끼리 겹치지 않는다. 문제 대상과 선택 대상은 기본 장면에서 식별된다.
- 증거: `small-mobile-world.png`, `mobile-world.png`, `landscape-mobile-world.png`.

## UI-04 · P1 · 이상 시설의 상태 언어가 작은 색점에 의존한다

**관측.** Cloudflare 실물에서는 01·05·07번의 색점과 얇은 테두리가 달라지지만, 무슨 상태인지 판 위에서는 나타나지 않는다. 13번에 생긴 문제도 초기 캡처에서 정상판과 같은 모양이며 색만 다르다. 상태 설명은 상세 패널을 열어야 나온다.

- 영향: 어느 시설이 왜 멈췄는지, 로그인 문제인지 확인이 필요한지, 지금 움직이는지 즉시 구분하기 어렵다. 흑백이나 색 구분이 약한 환경은 더 불리하다.
- 근거: `src/world/World.tsx:649`의 표식은 공통 원형 `.signal`과 번호이며, 심각도는 클래스·색으로 표현된다. `src/data.ts:40`은 서로 다른 오류를 danger/warning으로 묶는다. 지도 구역의 WCAG 1.4.1(색 사용) 문제다. 접근 가능한 이름이 있더라도 시각적 구분을 대신하지 않는다.
- 최소 개선: 문제에만 잠금/경고/정지 같은 서로 다른 형태와 짧은 상태를 붙인다. 정상 시설까지 상태 문장을 늘리지 않는다. 현재 실행 시설은 색 이외의 고정 형태나 진행 표시로 구분하고, 동작 줄이기에서도 의미를 보존한다.
- 합격: 흑백 화면에서 문제 시설·정상 시설·실행 시설을 서로 구분하며, 기본 화면에서 문제 시설을 눌렀을 때 바로 대응할 정보로 이어진다.
- 증거: `cloudflare-runtime-desktop.png`, `desktop-world.png`, `src/world/World.tsx:545`.

## UI-05 · P1 · 시설의 크기·재고·업무 상태 관계가 약하다

**관측.** 계정마다 건물 실루엣은 다르지만 번호만 보이므로, 어느 작업동이 어느 콘텐츠 계정인지 첫 화면에서 연결되지 않는다. 물탑·풍차·태양광·적재장은 업무 상태와 무관하게 고정 배치다. 계정별 재고 상자는 `ceil(min(ready,120)/20)`로 6개에서 포화하지만 상세의 목표는 300개다. **120개와 300개는 지도상 같은 적재량**이다.

- 영향에 대한 추론: 재고를 채울 계정, 제출을 기다리는 곳, 막힌 곳을 공간만으로 비교하기 어렵다. 업무 정보는 주로 패널의 숫자에서 얻는다. 실제 운영자의 학습 후 식별 능력은 시험하지 않았다.
- 근거: `src/world/World.tsx:38`의 13개 모델은 계정 순서로 연결된다. `World.tsx:550`의 재고 포화, `:371` 이후의 고정 기반 시설. 계정명은 `:667` hover/focus tooltip에만 표시된다.
- 최소 개선: 시설에는 짧은 계정 별칭이나 대표 콘텐츠를 식별 표식으로 연결한다. 재고 표현은 `ready/target`에 맞추고, 심사·제출 대기는 서로 다른 작은 구역이나 운송 상태로 연결한다. 실제 연결이 없는 장식 시설은 의미가 있는 조형으로 줄인다. 가짜 이동이나 가짜 생산량은 만들지 않는다.
- 합격: 동일한 계정의 재고를 0·120·300, 제출 대기·심사 중·오류로 바꾼 fixture에서 세계의 변화가 서로 구분된다. 전체 화면에서 처리할 계정을 골랐을 때 선택한 근거를 설명할 수 있다.
- 증거: `desktop-world.png`, `tablet-world.png`, `desktop-account.png`; `src/world/World.tsx:550`.

## UI-06 · P2 · 수치는 중복되고 작은 화면에서 수치의 이름이 빠진다

**관측.** 상단 287·240과 하단 비축 287·심사 240이 같은 데이터를 반복한다. 작은 화면에서는 상단의 `제출 가능`, `심사 중`, `공개`가 숨겨져 서로 비슷한 패키지·방패 아이콘과 숫자만 남는다. `검수`·`심사`는 서로 다른 업무인데 방패 아이콘도 공유한다. 오류 진입은 좌측 경고와 하단 메뉴 양쪽에 있다.

- 영향: 보이는 요소를 줄이지 않고 뜻을 읽는 단서만 줄인 상태다. 공간은 HUD에 쓰면서 어떤 숫자인지 기억해야 한다. 반복 진입 자체가 모두 잘못은 아니나, 현재 화면에서는 중복 수치와 함께 우선순위를 흐린다.
- 근거: `src/App.tsx:259`, `:354`; `src/style.css:1669`가 수치 이름을 숨긴다.
- 최소 개선: 전체 운영 수치와 생산 흐름 중 하나를 기본 HUD로 선택한다. 핵심 수치의 짧은 이름은 유지한다. 업무 흐름을 남기려면 고정 화살표 장식 대신 현재 정체 지점을 보여 주게 한다. 기존 상세 정보·복구 진입은 보존한다.
- 합격: 각 상시 숫자는 한 번만 나오고, 새 사용자가 툴팁 없이 숫자의 의미를 구별한다. 문제·다음 행동은 중복 수치보다 먼저 보인다.
- 증거: `desktop-world.png`, `mobile-world.png`, `small-mobile-world.png`.

## UI-07 · P2 · 보조 텍스트와 오류 숫자의 대비·글자 크기가 낮다

**계산+관측.** CSS 색을 WCAG 상대 휘도로 계산했다. 비활성 dock 텍스트 `#6c7e6d / #fbfcf7`는 **4.21:1**, 패널 보조 텍스트 `#6c7971 / #fbfcf8`는 **4.42:1**, 오류 숫자 `#ffffff / #b9773a`는 **3.64:1**이다. 모두 보통 글자 4.5:1에 미달한다. dock는 실제 반투명 배경이므로 장면별 결과는 달라지지만, 불투명 바탕의 유리한 조건에서도 통과하지 못한다. 메뉴 10~11px, 이메일 11px, 상태별 숫자 설명 10px가 실물에서 작게 보인다.

- 영향: 오류 건수와 메뉴, 계정 식별 보조 정보의 읽기 부담이 커진다. `WCAG 1.4.3`에 해당한다. 작은 글자 자체를 WCAG 위반으로 단정하지 않는다.
- 근거: `src/style.css:498`, `:517`, `:633`, `:763`, `:1997`; `ui/inspection.json`.
- 최소 개선: 실제 합성 배경 기준 4.5:1 이상을 확보하고, 작은 숫자·메뉴는 가능하면 12~14px 단계로 올린다. 핵심 업무 본문은 16px를 기준으로 실제 밀도를 조정한다. 글을 키워 넘치게 한 뒤 잘라 내는 방식은 피한다.
- 합격: 기본·선택·경고·비활성 상태의 실제 캡처 색 측정이 기준을 충족하고, 360px에서 중요 이름·건수·행동이 확대 없이 읽힌다.
- 증거: `mobile-world.png`, `mobile-account.png`, `ui/inspection.json`.

## UI-08 · P2 · 모바일 핵심 도구가 프로젝트의 44px 터치 기준에 못 미친다

**소스 확인.** 모바일 지도 레이어는 최소 `38×32px`, 카메라는 `38×40px`, 표식은 최소 `45×40px`, 상단 새로고침은 너비 35px다. 태블릿 카메라는 `42×42px`다. 실제 오탭을 관측한 것은 아니다.

- 영향에 대한 추론: 이동·확대 중 사용자가 작은 도구를 눌러야 하며, 인접 레이어 탭과 조작 구분이 어렵다.
- 근거: `src/style.css:1821`, `:1872`, `:1933`, `:2081`. 44px는 이번 프로젝트의 제작 기준이며, 이를 WCAG 2.5.8 AA의 최소값과 혼동하지 않는다. WCAG 2.5.5는 AAA다.
- 최소 개선: 보이는 아이콘은 작게 유지해도 실제 버튼과 간격을 최소 44×44px로 만든다. 지도 표식을 크게 늘리는 것만으로 UI-03을 악화시키지 말고 밀도를 함께 조정한다.
- 합격: 360px·390px·768px의 해당 버튼 실제 bounding box가 44px 이상이며 서로 겹치지 않는다.
- 증거: `mobile-world.png`, `tablet-world.png`, 위 CSS 위치.

## UI-09 · P2 · 재료·지형의 마감이 요청한 기준작 수준을 뒷받침하지 못한다

**시각 판단.** 건물은 준비된 산업용 저폴리 팩의 서로 다른 모델로 단지는 성립한다. 그러나 전체 장면의 채도·명도 차가 약해 도로·대지·지붕이 비슷하게 읽히고, 운하는 가장자리 맥락 없이 큰 청록 사각판으로 끝난다. 세로 PC에서 그 판이 제목 뒤를 크게 가로지른다. 풍차·태양광·물탑은 시선을 차지하지만 업무로 이어지는 조작이 없다. 상자를 읽으려면 크게 확대해야 하는데 기본 화면은 그보다 훨씬 작다.

- 영향: 모델 파일이 실제로 연결됐다는 사실과 별개로, 업무시설·배경·진행 표시의 시각 위계가 약하다. 사용자가 말한 장인급 경영 게임의 완성도를 현 상태에서 충족했다고 보고할 근거가 없다.
- 최소 개선: 먼저 UI-05의 업무 연결을 정한 뒤, 핵심 시설·도로·배경의 명도와 축척을 분리한다. 운하를 남기면 둑·수면·지형 연결을 정리하고, 의미가 없다면 화면을 차지하지 않게 줄인다. 실제로 읽히는 대표 시설 한 곳과 전체 장면을 고품질로 마감한 뒤 같은 규칙을 확장한다. 무거운 실사 PBR이나 효과 추가를 기본 처방으로 삼지 않는다.
- 합격: 전체·근접 화면에서 핵심 시설의 실루엣과 진행 상태가 구별되고, 동일 장면의 선택한 상용 기준작과 나란히 놓아 구도·재료·표식·조작의 차이를 설명할 수 있다. 모바일 성능도 그 최종안에서 다시 확인한다.
- 증거: `desktop-world.png`, `portrait-pc-world.png`, `mobile-world.png`; 모델 출처 `ASSETS.md:5`.

공식 [Cities: Skylines II 기능 안내](https://www.paradoxinteractive.com/games/cities-skylines-ii/features)와 [shapez 2 공식 소개](https://shapez2.com/)를 열람했다. shapez 2가 공개한 건물 내부 동작·생산 흐름·문제 지점 가시성은 이번 업무 지도에도 유효한 비교 관점이다. 이는 기능 설명을 통한 추론이며 해당 게임의 직접 플레이나 같은 조건의 캡처 비교를 했다는 뜻은 아니다. 공식 이미지 직접 다운로드는 도구 정책에 막혀 수행하지 않았고, 사용자 Chrome을 제어하는 우회는 하지 않았다. 기준작을 실제로 시각 대조하지 못했으므로 절대적인 상용 동급 점수는 매기지 않았다.

기존 자동화 시험의 통과를 무효로 하지는 않는다. 다만 현재 시험은 `document.scrollWidth <= innerWidth`를 확인하므로 화면 밖 dock나 특정 계정의 프레임 밖 위치까지 검증하지 못한다(`tests/world.e2e.ts:104`). 정지 이미지의 심사와 실제 사용자의 과업 성공률은 별개다. 물리 기기의 터치·발열·가독성, 보조 기술, 375px 정확한 화면은 이번 검토에서 미확인이다.

수정 순서는 **초기 화면 잘림·카메라 맞춤 → 표식과 상태 언어 → 업무 데이터의 공간 연결 → HUD 덜기 → 대비·터치·장면 마감**이 적절하다. 큰 렌더 효과를 추가하는 것만으로는 위 반려 사유가 없어지지 않는다.
