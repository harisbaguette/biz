# 원래 목적·사용자에게 남는 수고 검토

판정: **OUTCOME_REWORK**

2026-10-18 현재 소스, 문서, 실제 렌더 캡처와 기존 실행 검증을 대조했다. 이번 요청은 전문가 혹평이므로 제품·설정·운영 데이터는 수정하지 않았다. 실제 사용자 연구나 사용자의 만족도 조사 결과가 아닌 전문가 대리 평가다.

## 완료 주장을 막는 문제와 중요한 보완

### P-01 · 높음 · 공간이 사업의 병목을 설명하는 역할까지 맡지 못한다

**채워지지 않은 필요:** 사용자는 경영·산업 게임처럼 한눈에 현 상태를 읽고 다음 지시를 내리는 경험을 원했다. 현재 공간에서 직접 읽히는 운영 의미는 계정 번호/신호, 계정별 재고 상자, 실제 업로더 가동 시 트럭이다. 제작·검수·메타데이터의 공정별 물량과 정체는 해당 시설이나 흐름으로 연결되지 않는다. 컨테이너 적재장·풍차·태양광·급수탑은 운영 데이터와 무관한 고정 배치다. `docs/PLAN.md`가 말한 중앙 제작 시설·심사 출하장과 원래 목적 사이에도 차이가 있다.

**사용자에게 남는 수고:** 단지가 조용할 때 “비축을 채우는 중인지, 검수에서 막혔는지, 제출 한도 때문에 기다리는지”를 판단하려면 지도 대신 여러 패널을 열어 숫자와 상태를 조합해야 한다. 별도 관제를 안 보게 됐다는 원래 불편이 해소됐다고 확정하기 어렵다.

**근거:** `src/world/World.tsx:314`(계정별 시설), `:380`(고정 적재장), `:479`(업로더 기반 트럭), `:550`(상자 수), `src/App.tsx:353`(공정 버튼), `docs/PLAN.md:7`, 위 PC·모바일 실제 캡처. 게임 G05·09와 UI-05는 같은 공간 의미·척도 문제를 독립적으로 지적했다. 고객 C03·04도 실제 변화 확인과 계정 번호 암기에 남는 수고로 연결했다.

**필요한 수정/확인:** 실제 공정의 비축·대기·진행·정체 중 사용자의 결정에 필요한 최소 상태를 대응 시설과 연결한다. 계정은 작업동으로 남기되 어떤 공정에서 왜 멈췄고 누르면 무엇을 할 수 있는지 읽혀야 한다. 가짜 물류·점수·움직임을 덧붙일 필요는 없다. 검증은 대표 정상/막힘/복구 상태에서 “다음에 무엇을 할지”를 화면만 보고 고를 수 있는지로 한다.

### P-02 · 높음 · “출하 일정”이 다음 실제 제출 계획을 보여 주지 않는다

**채워지지 않은 필요:** 제출 예정분·제출·일정 관리를 요청했다. 현재는 이전 제출→예상 심사와 사용자 메모/재확인 예약이다. 원본 `next_upload_on`을 수집하고도 화면에서 쓰지 않는다. 실제 제출 예약·제출 묶음 선택·예정 수량 편집은 구현돼 있지 않다. 후자의 모든 기능이 필수라고 사용자가 세부 지정한 것은 아니지만, 현재 일정 기능만으로 제출 계획까지 관리한다고 읽히는 주장은 넓다.

**사용자에게 남는 수고:** “13계정 중 다음에 누가 언제 제출하며 준비 재고가 충분한가”를 여기서 끝내지 못해 원본 일정이나 기억으로 보충해야 한다. 재확인 예약을 실제 제출 예약으로 오해하면 예약 시각과 실제 제출 시각이 어긋날 수 있다.

**근거:** `connector/snapshot.py:34`, `src/types.ts:63`, `src/ui/Panels.tsx:530`(표시 항목), `:902`(일정 종류), `worker/index.mjs:479`(memo/recheck만 허용), `README.md:11`, `:15`. 고객 C01은 4번 재고 19/목표 300·심사 중 20개를 읽을 때 원본의 마지막 관측 한도 20/20과 관측 시각(3일 전)이 화면에서 빠짐을 확인했다. 이는 현재 제출 불가를 입증하는 값이 아니라 최신성까지 구별해 판단해야 하는 자료다. C07은 출하 일정 이름과 실제 예약 범위의 차이를 같은 문제로 지적했다.

**필요한 수정/확인:** 원본의 다음 제출 예정일과 그 성격을 계정/일정에서 먼저 드러낸다. 계정별 제출 가능분과 심사 한도·대기 이유를 그 일정에 연결한다. 실제 제출 일시 변경까지 맡길 것인지 범위는 원본이 지원하는 안전한 조작을 기준으로 정하고, 현재 지원 범위는 재확인 예약으로 명확히 읽히게 한다. 신규 위험한 제출 명령을 즉시 추가하라는 뜻은 아니다.

### P-03 · 높음 · 지시 반영과 실제 업무 결과 사이에서 관제의 행동 고리가 끊긴다

**채워지지 않은 필요:** 현 상태 인지→지시→정상 복구/실제 처리 확인이 한 흐름이어야 한다. 현재 `applied`는 자동화 설정 파일 저장 또는 재확인 요청 기록의 완료다. 이를 실제 제출 성공과 구별한 안내는 정확하다. 그러나 수집한 실제 제출·심사 `recent` 이벤트를 화면에서 쓰지 않고, 지시와 이후 관측 결과를 연결하지 않는다. `확인할 일`에서 최근 지시의 반영/실패를 볼 수 있는 것만으로 “내 지시가 실제 문제를 풀었나”가 닫히지는 않는다.

**사용자에게 남는 수고:** 재확인 지시 후 여러 계정의 상태와 시각을 다시 비교하거나 원본을 열어야 한다. 지난번 방문 이후 무엇이 실제 완료됐는지 구분하기 어렵다. 이는 기술적 명령 전달 버그와 별개의 제품 목적상 빈칸이다.

**근거:** `connector/bridge.py:25`(반영의 의미), `connector/snapshot.py:36`·`:103`(실제 이벤트 수집), `src/types.ts:68`, `src/ui/Panels.tsx:652`(최근 지시), `README.md:15`. `src`에서 `recent`는 타입 선언 외 사용되지 않는다. 독립 UX03은 동일 계정 재확인 2회가 격리 DB의 대기 명령 2개로 쌓이고, 해당 계정 화면에서는 전후 상태가 바뀌지 않는 것을 직접 재현했다.

**필요한 수정/확인:** 지시 수신/설정 반영, 실제 작업 대기/진행, 이후 관측 결과를 짧은 상태로 연결한다. 이미 있는 실제 이벤트·계정 관측 시각을 먼저 이용하고 지시 인과를 입증할 수 없을 때는 단정하지 않는다. 해당 계정으로 바로 돌아가 결과를 볼 수 있어야 한다.

### P-04 · 중간 · 문제를 알리는 것에 비해 복구를 끝내는 안내와 분기가 약하다

**채워지지 않은 필요:** 정상/문제 인지를 넘어 다음 지시의 기반이 되어야 한다. 로그인 필요에는 해당 브라우저에서 로그인하라는 안내가 있지만 관제에서 가능한 조작은 재확인이다. 원본 작업기 오류에는 “자동 복구를 기다린다”가 공통 안내이며 저장 공간·서비스 대기 등 원인에 따른 조치의 차이가 작다. 실패한 예약은 처리 실패 상태로 남고 해당 화면에서 다시 시도/수정/취소로 정리하는 조작이 없다.

**사용자에게 남는 수고:** 모바일에서 본 문제를 해결하려고 맥의 특정 브라우저·원본 로그·파일 위치를 다시 찾아야 한다. 기다려야 하는 상태인지 사람이 처리해야 하는 상태인지 추가 해석이 필요하다. 외부 로그인 자체를 자동화해야 한다는 뜻은 아니다.

### U-02 · “밤새 보게 되는” 반복 사용의 근거

현재 자료는 로딩·버튼·저장·오류 방어의 동작을 입증한다. 재미·다시 찾게 되는지·판단 시간을 줄이는지의 직접 근거는 없다. 기능 검증 통과를 재미의 실패나 성공으로 바꿔 말할 수 없다. 대표 업무인 ①오늘 막힌 곳 찾기 ②다음 제출과 재고 확인 ③지시 후 실제 처리 확인을 새로 들어온 운영자가 안내 없이 수행할 수 있는지, 두 번째 방문에서 변화가 읽히는지 확인하는 것이 먼저다. 장식·보상 점수 추가를 요구하는 판정은 아니다.

## 선택적 개선·현재 범위 밖

- 게임/그림·멤버십/YouTube/블로그의 실제 데이터 연동을 이번에 모두 끝내야 한다고 확대하지 않는다. 사용자가 첫 연동을 미리캔버스로 정했다. 두 번째 사업을 붙일 때 공통 상태·행동·이벤트와 사업별 데이터 경계를 정하고, 등록된 미연결 사업을 수정/삭제할 수 있게 하는 일은 후속 확장 작업이다.
- 수익·매출·원가·레벨·경험치·가상 화폐는 요청하지 않았다. 없는 기능이라는 이유로 결함을 만들지 않는다.
- 특정 유료 에셋을 썼는지 여부만으로 프로 품질을 판정하지 않는다. CC0 모델도 실제 연출·가독성·조작·정보 의미로 평가해야 한다. 사용자가 요청한 상용 수준과의 구체적 차이는 해당 분야 심사의 근거를 쓴다.
- 모든 상태를 한 번에 보이게 하거나 테이블·차트·세부 설명을 상시 늘리는 개선은 원래 방향과 충돌할 수 있다. 핵심 상태와 다음 행동을 먼저 고르고 중복을 덜어낸다.

## 권고 우선순위

1. **신뢰와 사용 차단:** 개별 재고·작업기 상태의 진실성, 초기 화면의 메뉴 잘림·계정 이탈·선택 실패를 우선 확인하고 바로잡는다. 집계 수량 일치나 기존 시험 통과로 현재 반례를 덮지 않는다.
2. **행동 완료와 공간의 역할:** 지시 반영/실제 업무 결과, 문제별 복구, 다음 제출 일정과 재고 의미를 연결한다. 장면에서 공정·정체를 읽고 객체를 선택해 해당 행동으로 도달하게 만든다. 공정 바·상단 수치·하단 메뉴의 중복은 이 흐름에 맞춰 줄인다.
3. **현장 기기와 실제 운영:** 외부 인증 이후 도메인·상시 연결을 적용하고, 실제 모바일·태블릿과 재연결을 확인한다. 배포 미완료와 시각 품질의 차이를 분리한다.
4. **장기간 확장:** 첫 사업의 흐름이 닫힌 뒤 공통 사업 단위와 두 번째 실제 연동으로 확장성을 입증한다.

평균 점수로 판정을 덮지 않는다. 현재 근거는 실데이터 관제의 작동 기반을 지지하지만, “최소한의 조작으로 사업을 읽고 실제 결과까지 관리하는 산업 게임급 통합 관제”가 완성됐다는 주장까지 지지하지 않는다. 이번 검토 요청 자체는 위 근거와 실행 가능한 보완 판단으로 충족하며 제품 수정은 수행하지 않았다.
