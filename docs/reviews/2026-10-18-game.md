# Three.js 산업 관제 플레이 심사

**PLAYTEST_REWORK. 현재 결과는 사용자가 요청한 상용 경영게임 수준에 미달한다.** 정지 화면의 확대 버튼이 실제 장면을 다시 그리지 않고, 회전하면 계정 번호가 건물에서 떨어진다. 그 두 조작부터 신뢰할 수 없다. 업무를 공간에서 읽고 조치하는 재미도 아직 얕다. 13개 건물 선택은 주로 숫자 패널을 여는 역할이며, 제작·검수·비축·심사의 관계는 장면보다 별도의 2D 메뉴에 남아 있다.

심사일 2026-10-18. 대상 `http://127.0.0.1:4317`. 제품 파일은 수정하지 않았다. 운영 API 변경은 하지 않았고, 지시 시험은 모든 `/api/**`를 메모리 DB로 가로챈 별도 브라우저에서만 실행했다. 썸네일은 실제 서버의 읽기 전용 GET을 사용했다.

## 확인 범위와 한계

| 대상 | 확인한 수 | 증거 |
|---|---:|---|
| 계정 건물 선택 | 13개 중 13개 | `game/play.mjs`의 순차 선택 루프, 루프 이후 `desktop-account13.png` |
| 화면 크기 | 5개 중 5개 | 1440×900, 900×1440, 844×390, 390×844, 768×1024. 각 `*-initial.png`와 `initial-observations.json` |
| 조작 항목 | 12종 중 10종 | 건물 선택, 확대 버튼, 회전 버튼, 캔버스 팬, 초기 시점, 우클릭, 모바일 pinch, 번호 위 드래그, 격리 지시 접수, 재진입. 긴 누르기와 두 손가락 회전은 미확인 |
| 모델 | 24개 로드 확인 | `camera-gestures.json`의 `loaded:24`. 24개 모델 원본의 개별 아트 검수는 하지 않음 |

Chromium `headless:true` 한 인스턴스씩 실행했다. 다른 전문가의 브라우저 검사가 병렬로 있었으므로 FPS·응답 시간을 실제 기기 성능으로 판정하지 않았다. 아래 `totalFrames`는 속도 측정이 아니라 입력 뒤 렌더 호출 유무를 확인한 값이다. 물리 휴대전화·태블릿의 터치감과 발열은 미확인이다.

장시간 실행 스크립트 `play.mjs`는 지시 접수 뒤 배지 숫자를 포함한 버튼의 정확 이름을 잘못 지정해 후반에 중단됐다. 앱 오류로 세지 않았다. 이 실행의 개별 계정 제목 배열은 파일로 남지 않았고, 마지막 13번 선택 캡처와 실행 스크립트가 남았다. 이후 좁힌 `camera-gestures.mjs`는 정상 종료했고, 브라우저를 닫았다. 적용 성공·실패를 가장한 운영 원본 변경은 하지 않았다. `command-pending-after-refresh.png`는 여전히 접수 대기 상태이며 적용 완료 근거가 아니다.

## 문제 전체

### G01 · P1 · 확대 버튼이 화면을 확대하지 않는다

- **재현:** PC에서 장면 로드 후 정지 상태를 기다린다. `확대`를 한 번 누르고 2.1초 기다린다.
- **관찰:** `camera-gestures.json`에서 카메라 `zoom`은 `1 → 1.2180676879157946`으로 바뀌지만 `totalFrames`는 `2 → 2`다. 버튼을 눌렀다는 hover 반응만 있고 공장 크기는 같다. `zoom-before.png`, `zoom-after.png`를 직접 대조했다.
- **코드:** `src/world/World.tsx:282`는 `targetZoom`을 바꾸지만 그리기 요청을 세우지 않는다. `:514`의 보간도 `dirty`를 갱신하지 않고, 실제 그리기는 `:533`에서 `dirty`에 종속된다.
- **영향:** 가장 기본적인 조작을 눌러도 반응이 없다. 이후 다른 갱신에서 뒤늦게 확대될 수 있어 사용자는 버튼과 화면을 믿기 어렵다.
- **최소 개선:** 카메라 보간 중 장면과 DOM 투영을 함께 갱신하고, 보간이 끝나면 다시 쉬게 한다. 버튼 값이 바뀌었다는 검증으로 끝내지 않는다.
- **합격 기준:** 서버 응답·상태 갱신 없이 정지 장면에서 확대와 축소 각각을 눌렀을 때, 렌더 수와 실제 공장 픽셀이 즉시 변한다. 빠르게 여러 번 눌러도 최종 배율이 의도한 입력 횟수에 대응한다.

### G02 · P1 · 회전하면 번호와 건물이 분리된다

- **재현:** PC 초기 장면에서 `시점 회전`을 한 번 누르고 0.5초 이상 기다린다.
- **관찰:** 건물은 회전하지만 번호 라벨은 화면 왼쪽과 화면 밖으로 날아간다. `desktop-rotated-static-compass.png`, `rotate-final.png`. 마지막 재현의 01 라벨 x는 약 `-355px`였다. 건물이 화면 안에 있는데 어떤 계정인지 번호로 식별할 수 없다.
- **원인 추론:** `src/world/World.tsx:555`에서 `project(camera)`를 실행한 뒤 `:564`에서 렌더한다. 그때 DOM 투영이 이전 카메라 행렬을 사용하고, 그리기 후 `dirty=false`여서 잘못된 번호 위치가 정지하는 순서 문제다. 재현은 확정이고 행렬 갱신 순서는 수정 담당자가 확인할 원인이다.
- **영향:** 지도 객체의 정체성과 선택 위치가 깨진다. 회전 뒤 엉뚱한 번호를 선택하거나 아예 선택 대상을 잃을 수 있다. 하단 N 나침반도 `src/App.tsx:346`의 고정 문자여서 회전 방향을 설명하지 못한다.
- **최소 개선:** 카메라 행렬 갱신을 마친 동일한 상태로 장면과 번호를 투영한다. 사용하지 않는 고정 나침반은 없애거나 실제 방위와 연결한다.
- **합격 기준:** 정지 상태에서 연속 회전과 리셋을 반복해도 13개 번호가 각각 자기 건물의 지정 위치에 남는다. 원근/직교 행렬 값 확인에 더해 캡처상의 위치까지 대조한다.

### G03 · P1 · 세로 PC에서 ‘전체 단지’가 전체가 아니다

- **재현:** 900×1440으로 처음 접속하고 2.2초 안정화한다.
- **관찰:** 09 라벨의 x=`-56.45`, 폭=`51.78px`다. 번호 전체가 왼쪽 화면 밖에 있고 관련 시설도 잘린다. `portrait-pc-initial.png`, `initial-observations.json`. 나머지 보이는 번호만으로는 작업동이 빠졌다는 사실도 빨리 알기 어렵다.
- **코드:** `src/world/World.tsx:590`은 가로 폭 구간에 따른 고정 span을 사용한다. 단지 경계와 가로세로 비율로 전체를 맞추지 않는다. 리셋 `:289`도 고정 배율 1로 돌아갈 뿐이다.
- **영향:** 사용자가 명시한 세로 모니터 최적화와 한눈에 13계정을 보는 목적을 어긴다.
- **최소 개선:** 단지 경계와 화면의 실제 유효 영역으로 초기·리셋 시점을 맞춘다. 부제·도구·시트가 차지한 자리도 유효 영역에서 고려한다.
- **합격 기준:** 다섯 확인 크기의 초기·리셋 상태에서 13개 번호와 주요 시설이 모두 보이고 누를 수 있다. 900×1440에서 09 선택을 위해 먼저 팬을 배워야 하지 않는다.

### G04 · P1 · 가로 모바일에서 핵심 메뉴가 화면 아래로 잘린다

- **재현:** 844×390으로 처음 접속하고 2.2초 안정화한다.
- **관찰:** dock는 y=`373`, 높이=`57px`다. 화면 아래 40px가 잘려 작업동·재고·일정·확인할 일·운영 메뉴가 제대로 보이지 않는다. `landscape-mobile-initial.png`, `initial-observations.json`.
- **영향:** 공장은 보이지만 관리할 메뉴를 사용할 수 없는 진입 화면이다. 사용자가 어떤 방향으로 잡아도 동작해야 한다는 요구를 충족하지 않는다.
- **최소 개선:** 화면 높이와 safe area 기준으로 dock 배치를 고정하고, 가로 모드에서 단지·도구가 사용하는 공간을 다시 나눈다.
- **합격 기준:** 844×390 초기 화면과 패널을 연 뒤 모두 메뉴 전체가 화면 안에 있으며, 각 항목을 실제 탭할 수 있다. 가로 넘침이 없다는 검사로 대신하지 않는다.

### G05 · P1 · 경영의 핵심 관계가 3D 안에 없다

- **재현:** 초기 단지에서 제작이 막힌 곳, 검수 대기, 제출 가능한 재고, 심사 대기 중 어느 것이 다음 일을 막는지 장면만 보고 판단한다. 물탑·발전기·컨테이너 적재장을 눌러 본다. 계정을 선택해 지시를 접수한 뒤 패널을 닫는다.
- **관찰:** 실제 선택 대상은 13개 계정 건물이다. `src/world/World.tsx:219`는 `buildingGroup`만 picking하고, 계정 외 기반 시설·고정 컨테이너는 별도 장식으로 놓인다(`:380–405`). 제작·검수·비축·심사의 흐름은 `src/App.tsx:353`의 2D 버튼 줄로 표현된다. 접수 대기 지시도 장면에서 계정과 연결되지 않는다(`command-pending-map.png`).
- **판단:** 미니어처 공장을 보는 흥미 뒤에 실제 사업을 움직인다는 감각이 이어지지 않는다. 현재 주요 반복은 번호 클릭→패널에서 숫자 읽기→버튼→다른 메뉴에서 결과 확인이다. 사용자가 피하고 싶었던 관리 화면의 반복이 그대로 남는다. 장면의 많은 면적을 쓰는 도로·조경·기반 시설보다 작은 번호가 더 중요하다.
- **최소 개선:** 실제 제작/검수/제출의 상태가 있는 최소 공정만 공간의 시설·대기열에 대응시키고, 문제 시설 선택에서 원인과 가능한 한 가지 조치까지 이어지게 한다. 실제 접수/반영/실패 상태도 해당 객체에 연결한다. 의미가 없는 기반 시설과 중복 2D 흐름은 덜어낸다. 가짜 생산, 임의 보상, 허위 진행률을 넣자는 제안이 아니다.
- **합격 기준:** 처음 보는 사람이 첫 30초 안에 실제 병목 하나를 장면에서 찾아 그 대상의 근거와 조치까지 연결한다. 조치 결과를 확인하기 위해 메뉴를 뒤져야 하지 않는다. 정상일 때는 일이 없는 이유를, 오류 때는 개입할 대상을 공간의 같은 규칙으로 읽을 수 있어야 한다.

### G06 · P2 · 번호 위에서 시작한 드래그는 이동하지 않는다

- **재현:** 390×844에서 07 번호 중앙에 손가락을 대고 60px 오른쪽·70px 아래로 드래그한다.
- **관찰:** 맵은 이동하지 않고 패널도 열리지 않는다. 번호 위치 차이는 약 0.08px 미만으로, 리셋 보간의 잔여 수준이다. `camera-gestures.json`의 `beforeLabelDrag`/`afterLabelDrag`, `mobile-label-drag.png`. 같은 화면에서 캔버스 입력과 pinch는 동작했다.
- **코드:** `src/style.css:205`의 덮개 위 버튼은 `:228`에서 pointer events를 받는다. 이동 처리는 그 아래 canvas의 OrbitControls에만 붙어 있다(`src/world/World.tsx:106`).
- **영향:** 번호가 몰린 모바일 중심부에서 드래그를 시작하면 아무 일도 없다. 작은 화면을 더 확대·이동하려는 상황에서 가장 많은 터치 시작점이 막힌다.
- **최소 개선:** 탭과 드래그를 구별하고 번호에서 시작한 이동도 지도 입력으로 이어지게 한다. 탭 선택과 접근 가능한 버튼 동작은 보존한다.
- **합격 기준:** 빈 땅과 번호 위 어느 곳에서 시작해도 한 손가락 팬을 할 수 있고, 이동 임계값을 넘기면 계정 선택이 발생하지 않는다.

### G07 · P2 · 카메라를 돌릴 우클릭이 계정을 선택한다

- **재현:** PC 초기 화면에서 01 건물 지붕 부근을 오른쪽 버튼으로 눌렀다 뗀다.
- **관찰:** 회전용 오른쪽 버튼인데 01 계정 패널이 열린다. `desktop-rightclick-selects.png`.
- **코드:** `src/world/World.tsx:116`은 RIGHT를 ROTATE로 지정하지만, `:211`의 선택 처리는 `e.button`을 구별하지 않고 7px 이내 pointerup을 모두 선택으로 처리한다.
- **영향:** 시점을 조절하려다 의도하지 않은 계정을 선택하고 자동 초점 이동까지 발생한다. 산업게임 조작에서 카메라 조작과 업무 대상 선택의 경계가 불분명하다.
- **최소 개선:** 기본 버튼·단일 탭의 클릭만 선택으로 처리하고, OrbitControls가 소유한 회전·핀치·취소된 입력은 선택에서 제외한다.
- **합격 기준:** 우클릭과 짧은 우드래그는 계정 패널을 열지 않는다. 좌클릭 및 한 손가락 탭은 기존처럼 해당 건물을 선택한다.

### G08 · P2 · 지도에서 오류 종류를 색만으로 구별한다

- **재현:** 상태 모드에서 01·05·07 번호를 보고 로그인 필요와 차단을 구별한다.
- **관찰:** 동일한 원형 신호와 번호가 있고 차이는 주황·붉은색이다. hover 툴팁은 계정 이름이며 원인을 보여 주지 않는다(`src/world/World.tsx:661–667`). `desktop-initial.png`, `mobile-initial.png`.
- **영향:** 오류가 있다는 것은 알 수 있어도 무엇이 막혔는지 알려면 계속 눌러 읽어야 한다. 모바일에는 hover도 없다. 정상적인 심사 대기와 다른 정상 상태도 같은 초록색으로 압축된다.
- **최소 개선:** 오류에 잠금/경고 등 서로 다른 작은 형태를 적용하고, 선택 또는 초점에서 짧은 실제 상태와 원인을 보여 준다. 글을 늘리기보다 같은 원형 신호만 반복하는 표현을 바꾼다.
- **합격 기준:** 색을 제거한 캡처에서도 로그인 필요·업무 오류·작업 중을 구별하고 다음에 어느 대상을 확인할지 정할 수 있다.

### G09 · P2 · 재고 상자가 경영 판단에 필요한 규모를 전하지 못한다

- **재현:** 실제 재고 9개·44개인 계정들을 비교하고, 각 목표 300개 대비 충족 여부를 장면에서 판단한다.
- **관찰:** `src/world/World.tsx:550`은 상자 하나를 20개 단위로 올림하고 최대 120개에서 여섯 상자로 포화시킨다. 목표는 300개다. 120개와 300개도 같은 여섯 상자가 된다. 실제 화면의 상자는 매우 작고 목표 공간이나 부족량을 같이 표현하지 않는다. 재고 레이어는 숫자를 추가할 뿐 이 규칙을 설명하지 않는다.
- **판단:** 정확한 수량은 패널로 제공되지만, 공간 재고 표현은 어떤 계정을 먼저 채울지 판단하는 단서로 약하다. 풍경에 상자가 놓였다는 인상에 머문다. 임의적인 포화값이 목표 달성과 혼동되면 특히 문제가 된다.
- **최소 개선:** 실제 계정 목표를 같은 공간 용량에 대응시켜 부족/충족의 차이를 읽히게 한다. 정확 수량은 선택 시 하나만 보여 주고, 120개에서 포화시키는 별도 척도를 없앤다. 모델 수를 실제 수량만큼 늘릴 필요는 없다.
- **합격 기준:** 0/9/44/120/300개 시험 상태에서 부족과 목표 충족이 장면만으로 분명하고, 120개를 목표 충족으로 오해하지 않는다. 실제 수량은 항상 확인할 수 있다.
