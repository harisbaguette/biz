## 수정 확인 R1 — 청크 누락 뒤 정상 수신 복구

수정 위치: `worker/index.mjs:204`.

이전 수정본은 새 스냅샷 POST 전에 기존 자산 전체를 복원해 청크 누락 시 새 수신도 503으로 거절했다. 현재는 기존 메타데이터의 관측 시각만 읽어 새 전체 데이터를 교체할 수 있다.

최종 독립 재현:

1. 메모리 DB에 유효한 스냅샷 게시 → 200.
2. 그 메모리 DB의 자산 청크만 삭제.
3. `/api/world` → **503**.
4. 더 새로운 유효한 전체 스냅샷 POST → **200**.
5. `/api/world` → **200 복구**. 과거 시각 수신은 **409**, 깨진 메타데이터의 정상 재수신도 **200**.

청크가 실제 운영에서 이미 손상됐다고 주장하지는 않는다. 새로 추가한 청크 누락 감지 조건에서 수신 복구가 되지 않는 입력 반례다.

판정: 청크 누락 감지와 정상 재수신 복구, 과거 시각 거부를 모두 통과했다.

## 수정 확인 R2 — 합쳐진 요청 ID의 완료 후 재시도

수정 위치: `worker/index.mjs:136`, `worker/index.mjs:145`, `worker/index.mjs:150`, `worker/schema.sql`의 `command_requests`.

이전 수정본은 B를 대기 중 A에 합쳐 응답하면서 B를 저장하지 않아, A 처리 뒤 B 재시도 때 새 지시가 생겼다. 현재는 요청 ID→실행 ID를 `command_requests`에 보존하며 동시 지시 선택·alias 등록을 한 batch로 묶는다.

최종 독립 재현: 업로드 일시정지 A 게시 **201** → 같은 동작의 B 게시 **200, id=A** → A 반영 완료 → B 재전송 **200, id=A, status=applied**, 새 대기 지시 **0개**. B의 다른 내용 재전송은 **409**다.

판정: 합쳐진 요청 ID의 완료 후 재전송을 통과했다. 추가 회귀는 동시 16개 요청 ID 모두를 완료 후 재전송해도 새 지시가 없음을 확인한다.

## 수정 확인 R3 — 인증된 최대 미리보기 재시도 쿼리

수정 위치: `worker/index.mjs:493`.

이전 수정본의 인증된 최대 재시도는 51쿼리였다. 현재는 실패 기록 24개를 한 `DELETE ... IN (...)`으로 지워 총 **28쿼리**다. 기존 48건 실패 회신(49쿼리)과 25건 성공 회신(27쿼리) 회귀도 통과했다.

최종 독립 재현은 실제 `LOCAL_MODE=false`와 유효한 임시 세션의 `{ids:24개,retry:true}`를 실행해 **28쿼리·202**를 계수했다. 요청당 50쿼리 초과 시 오류를 던지는 어댑터에서도 **202**다. 실제 Cloudflare 한도 실패를 주입한 것은 아니고 대상 계정 요금제도 조사하지 않았다.

2026-10-18 확인한 [Cloudflare D1 공식 한도](https://developers.cloudflare.com/d1/platform/limits/)는 Free 50, Paid 1000 queries/invocation이다. 인증된 최대 요청의 코드 쿼리 수는 이 범위 안이다.

판정: 인증을 포함한 최대 요청의 코드 한도 검증을 통과했다. 실제 Cloudflare 동작은 미검증이다.

## 미검증

Cloudflare 실제 D1·HTTP 부하, 원본 PostgreSQL의 운영 이력 전체 정합성, 실제 업로더 중단, 설치된 개인 폴더의 연결 프로그램 갱신, 물리 기기와 화면 UX는 이번 재심으로 승인하지 않는다. 성능 보고의 p95는 메모리 SQLite 실험이라는 한계가 문서에 명시돼 있어 실서비스 성능 보장으로 해석하지 않았다.

배포 시 최신 `schema.sql`의 `preview_failures`, `command_requests`와 인덱스 추가를 먼저 반영해야 한다. 재전송 안전성을 유지해야 하는 운영 중에는 `command_requests` 기록을 지우면 안 된다. 설치된 연결 프로그램은 수정본으로 다시 설치·재시작한 뒤 새 실패 회신과 업로더 관측 값 수신을 별도 확인해야 한다.
