## F01 — 연결 프로그램 생존과 제출 작업기 생존을 혼동

위치: `src/data.ts:40`, `src/data.ts:54`, `src/App.tsx:151`, `connector/snapshot.py:85`, `connector/snapshot.py:107`.

연결 프로그램은 자동 운영 상태 파일을 읽고 새로운 `receivedAt`을 계속 보낼 수 있다. 화면은 그 수신 시각으로 연결을 판정하며 제출 작업기의 `lastPollAt`, `lastRunAt`, `nextAt`은 이슈 계산에 쓰지 않는다. 제작·검수·메타데이터 작업기에만 별도 시간 경과 검사가 있다.

재현: 제출 자동화 `enabled=true`, `lastPollAt/lastRunAt=2020-01-01`, `nextAt`도 과거, 연결 수신과 제작 lane만 현재 시각으로 둔다. 결과는 `transportStale=false, accountIssues=0, laneIssues=0`이다. 이전 계정의 `running=true`가 남으면 `severity=active`, `작업 중`도 계속 반환한다. 이 재현은 판정 함수 실행이며 실제 작업기를 죽인 시험은 아니다.

영향: 제출이 멈췄는데 관제에는 확인할 일이 없고 정상으로 보인다. 사용자가 원래 작업기를 다시 살피는 부담이 돌아온다.

최소 개선: 업로더 상태 파일의 갱신 시각·실행 서비스 생존 또는 heartbeat를 별도로 수집하고, 다음 순회 예정과 허용 지연을 고려해 멈춤을 판단한다. 업로더는 정상 대기 시 상태 파일을 매분 쓰지 않을 수 있으므로 단순히 3분을 적용하면 안 된다. 오래된 running은 실행 증거가 없을 때 ‘진행 확인’으로 낮춘다.

회귀 기준: (1) 다음 순회가 미래인 정상 대기는 오류가 아님, (2) 예정 시각과 허용 지연이 지난 무갱신은 경고, (3) 실행 중 표시는 실제 실행/heartbeat와 함께 만료됨, (4) 연결 프로그램만 살아 있어도 제출기 중단이 인지됨.

## F02 — 원본 상태 사전과 경고 판정 누락

위치: `src/data.ts:13`, `src/data.ts:43`, `src/data.ts:51`. 원본 근거: `미리캔버스 키워드 생성기/공장/local_worker/upload_automation.py:102`, `:108`, `:374`.

## F03 — 오래된 완료 이력이 앞으로 할 일을 숨김

위치: `worker/index.mjs:391`, 표시 영향 `src/ui/Panels.tsx:483`.

`SELECT * FROM schedules ORDER BY due_at LIMIT 300`은 상태와 관계없이 오래된 순서 300건만 반환한다. 완료·취소 기록을 UI에서 나중에 분리해도 그때는 이미 앞으로의 일정이 잘린 뒤다.

재현: 메모리 DB에 2020년 완료 일정 300건을 넣고 내일의 메모를 정상 API로 저장한다. 실제 결과 `createdStatus=201, returned=300, newPlanVisible=false, actualSaved=1`.

영향: 일정 저장 성공 뒤 목록에서는 사라진다. 일정 누적 사용으로 생기는 결함이며 사용자에게 일정 유실처럼 보인다. 재확인 일정이라면 보이지 않는 상태에서도 서버에서 지시로 전환될 수 있어 취소와 확인이 어려워진다.

최소 개선: 미완료 일정을 먼저 별도 조회하고, 완료·취소 이력은 별도 페이지네이션이나 최근 순서로 제한한다. 미완료 목록이 잘리면 더 보기와 전체 개수를 제공한다.

회귀 기준: 과거 완료 300건 이상과 미래 계획을 섞어도 새 계획이 보인다. 오래된 완료 기록 때문에 예정 업무가 결과에서 제외되지 않는다.

## F04 — 분할 저장은 원자적이지만 읽기는 원자적이지 않음

위치: `worker/index.mjs:84`, `:92`, `:191`, `:206`.

스냅샷 메타데이터와 자산 청크는 하나의 batch로 교체된다. 읽을 때는 메타데이터 SELECT와 청크 SELECT를 각각 await한다. 그 사이에 새 batch가 반영되면 이전 계정 요약과 신규 자산이 한 응답으로 묶인다.

재현: 첫 SELECT가 이전 메타데이터를 반환한 직후 정상 snapshot API로 신규 버전을 게시한 다음 청크 SELECT를 이어 가게 했다. 이 결정적인 실행 순서에서 `accountReady=1, assetTitle=new`가 반환된다. 둘 다 원래 각각 유효한 스냅샷이었다. Cloudflare 실제 부하에서 발생 빈도를 측정한 것은 아니며 동일 코드의 읽기 순서 반례다.

영향: 한 번의 관제 갱신 안에서 재고 숫자와 상세 목록이 맞지 않는다. 다음 수신까지 원인을 구분할 수 없다.

최소 개선: 청크에 불변 snapshot revision을 붙이고 메타데이터가 가리키는 revision만 읽거나, 플랫폼이 보장하는 한 읽기 트랜잭션으로 메타데이터와 청크를 함께 조회한다. 저장 batch만 묶어서는 읽기 일관성이 보장되지 않는다.

회귀 기준: `메타 N 읽기 → N+1 게시 → 재고 읽기`를 강제로 삽입해도 전체 N 또는 전체 N+1만 반환한다. 청크 누락도 조용히 정상 재고로 표시하지 않는다.

## F05 — 없는 그림이 뒤의 모든 미리보기 처리를 막음

위치: `worker/index.mjs:281`, `worker/index.mjs:438`, `connector/bridge.py:78`, `connector/bridge.py:91`.

서버는 가장 오래된 preview 요청 48개만 준다. 연결 프로그램은 파일이 없거나 이미지가 깨졌을 때 이를 건너뛰며, 실패 결과를 서버로 보내거나 순서를 뒤로 옮기지 않는다. 성공한 요청만 삭제된다.

재현: 실제 자산 ID 49개를 넣고 첫 48개를 없는 파일, 49번째를 정상 PNG로 구성했다. 서버 poll 3회 모두 동일한 앞 48개만 반환했다. 실제 `thumbnails()`로 생성한 결과는 큐 경유 0개, 정상 ID 단독 지정 시 1개다. 현재 자동 프리페치 대상에 없는, 이미 제출한/과거 그림을 입력으로 썼다.

영향: 한 페이지의 실패 파일이 뒤 페이지의 정상 그림까지 계속 빈 미리보기로 만든다. 누적 시 큐 상한에 도달해 새로운 요청도 429가 된다. 재시작만으로는 서버에 남은 요청이 없어지지 않는다.

최소 개선: 미리보기 실패·파일 없음 결과를 회신하고 유한 횟수 재시도/지연/만료 또는 요청 우선순위 순환을 둔다. 사라진 자산의 요청도 정리한다. 사용자는 계속 ‘가져오는 중’ 대신 실패와 재시도 가능 여부를 확인할 수 있어야 한다.

회귀 기준: 앞에 영구 실패 48건이 있어도 뒤 정상 요청이 정해진 시간 내 처리된다. 임시 NAS 단절은 무한 재시도와 영구 포기를 구분한다.

## F06 — 로컬 데이터 어댑터는 동시 batch를 처리하지 못함

위치: `server/db.mjs:21`, 같은 런타임 패턴 `server/local.mjs:35`.

단일 SQLite 연결에서 `BEGIN` 뒤 각 쿼리를 await하므로 다음 batch가 그 사이에 또 `BEGIN`을 실행할 수 있다. Cloudflare D1 자체의 결함이라는 주장은 아니다. 로컬 운영/미리보기와 로컬 API의 어댑터 문제다.

재현: 실제 `server/db.mjs` 어댑터를 메모리 DB에 연결하고 1건 insert batch 두 개를 `Promise.allSettled`로 동시에 실행했다. 2개 중 1개만 성공하고 나머지는 `cannot start a transaction within a transaction`로 실패했다. 저장 건수 1개. 이 예외가 API에서 발생하면 일반 500 응답으로 바뀐다. HTTP 동시 부하를 따로 측정하지는 않았다.

영향: 로컬 관제를 여러 탭/기기나 연결 프로그램이 동시에 쓰는 동안 일부 저장·수신이 실패할 수 있다.

최소 개선: 로컬 DB의 batch 실행을 직렬화하거나, 동기 SQLite 트랜잭션 전체를 await로 양보하지 않고 끝내도록 한다. 같은 패턴은 런타임 어댑터 2개와 시험용 사본 2개에서 발견했다. 이번 검토에서는 고치지 않았다.

회귀 기준: 독립 batch 다수를 동시에 시작해도 모두 반영되고, 한 batch가 실패할 때 다른 batch의 트랜잭션을 rollback하지 않는다.

## F07 — 포화 상태에서 멱등 재시도가 기존 결과를 받지 못함

위치: `worker/index.mjs:461`, 실제 중복 확인 `worker/index.mjs:113`.

대기 중 지시 20건 제한을 확인한 뒤에 같은 ID가 이미 있는지 검사한다. 따라서 이미 접수된 지시를 네트워크 문제 뒤 같은 ID로 재전송해도 기존 결과 대신 ‘대기 중 지시가 많습니다’ 429를 받는다.

재현: 유효한 지시 20개 저장 뒤 `command-0`의 같은 내용·같은 ID 재전송. 결과 429, DB 20건 유지. 중복 실행이 발생했다는 주장은 아니다.

영향: 접수 여부가 불명확한 네트워크 복구 시 성공한 요청도 실패처럼 보인다. 현재 UI는 각 버튼 전송 때 새 UUID를 만들어 완전한 요청 재시도 계약도 활용하지 못한다.

최소 개선: 기존 ID와 내용 확인을 큐 상한·연결 제한보다 먼저 하고, UI도 같은 전송의 재시도 동안 요청 ID를 유지한다.

회귀 기준: 큐가 차거나 후속 연결이 끊겨도 이미 저장된 같은 ID는 기존 결과를 반환하고, 같은 ID의 다른 내용만 409가 된다.

## F08 — 최근 제작물은 최신순이 아님

위치: `connector/snapshot.py:50`, `src/ui/Panels.tsx:308`.

스냅샷의 production 자산은 `ORDER BY a.id,p.updated_at DESC`로 전달된다. 계정 패널의 ‘최근 제작물’은 계정/미리보기 유무를 filter한 뒤 `slice(0,4)`만 하므로 최신 시각이 아니라 자산 ID 순으로 먼저 나온 그림을 보여 준다.

재현: ID `a,b,c,d,z`, 앞 4개는 2020년, `z`만 2030년이고 모두 미리보기가 있는 fixture에서 실제 표현식이 고르는 것은 `a,b,c,d`다. 최신 `z`는 없다. 이 항목은 작은 데이터 반례와 정적 경로 확인이며 새 브라우저 렌더를 하지 않았다.

영향: 새로 만든 그림을 즉시 확인하려는데 오래된 그림이 ‘최근’으로 반복 노출된다.

최소 개선: 계정/미리보기 필터 후 `updatedAt` 내림차순으로 정렬한 뒤 4개를 고른다.

회귀 기준: ID 정렬과 제작 시각이 역순인 데이터에서도 가장 최근 그림 4개가 보인다.

## 미검증 및 변경 경계

원본 데이터와 제품 파일을 고치지 않았다. 새로 쓴 파일은 이 보고서와 `artifacts/review-2026-10-18/functional/`의 재현·결과·검토 목록뿐이다. 라이브 API에는 읽기 1회만 요청했다. 기존 `npm test`의 운영 서버 확인도 임시 디렉터리와 별도 포트 4320을 사용해 종료했다.

물리 기기, 실제 Cloudflare 도메인, 실제 업로더 장애 주입, 원본 PostgreSQL 전체 이력의 정합성은 이번 결과로 검증됐다고 보지 않는다. Three.js 및 화면 포커스·통신 무응답의 브라우저 검토는 다른 전문가 결과를 사용한다.
