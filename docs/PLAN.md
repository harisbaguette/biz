# BLUEKITE WORKS 사업 게임

2026-10-23. 현재 기준은 [계정별 작업 사이클](owner-cycle-direction.md)과 [실제 데이터 의미](owner-cycle-data.md)다. 재고 숫자와 반복 창고를 강조했던 화면을 사용자 반려에 따라 다시 설계한다. 첫 판단은 **현재 심사 여부, 다음 제출 조건, 다음 확인·재시도 시각, 막힌 원인**이다.

혼자 운영하는 여러 사업을 한 공간에서 보고 다음 지시를 내린다. 첫 사업은 실제 운영 중인 미리캔버스 기여자 13계정이다. 계정의 제작, 사용 가능한 비축, 실제 제출, 심사 결과를 구분한다. 허위 성공 수치와 가짜 운영 움직임은 만들지 않는다.

## 화면

구현 구조는 [프런트엔드 안내](FRONTEND.md)를 따른다. 이전 설계와 사용자 반려의 이유는 [재기획 기록](owner-first-plan.md)에 남긴다.

세로 모바일의 전체 화면 Three.js 제작소에서 시작한다. 공유 제작기와 짧은 운반대, 13개 계정의 출고 그림·심사함·완료 보관, 월 수익 장부가 같은 바닥 위에 이어진다. 기본 전경에서 13계정의 심사·결과 예상 또는 막힌 원인·다음 시각을 함께 읽는다. 심사 0은 빈 작업판, 심사 중은 실제 제출 묶음으로 보인다. 재고 적재는 작은 출고 묶음으로 보조한다. 승인·공개된 실제 미리보기가 없으면 다른 단계의 그림을 대신 쓰지 않는다.

한 손가락으로 이동, 두 손가락으로 확대·축소한다. 모바일 회전은 잠그고 전체 보기로 복귀한다. 기본 화면에서는 13계정이 모두 보이며, 선택하면 같은 공간 안에서 해당 작업대에 집중한다. 닫으면 13계정 전경을 복구한다. 태블릿과 PC도 같은 공정 관계를 유지하며 화면 비율에 맞춰 배치한다. 긴 목록과 입력은 시설에서 여는 그림·일정·수익 장부에 둔다. WebGL 실패 시에도 13계정 목록과 복구 경로를 유지한다.

## 실제 연결

맥미니의 PostgreSQL `miricanvas_upload`를 읽기 전용으로 조회한다. 전체 PNG를 검사하는 기존 `/api/state`는 30초에 응답하지 않아 주기 조회로 사용하지 않는다. 현재 운영 정책의 `production_stock.inventory`로 목표와 공정을 읽고, `keyword_allocation.ready_count`의 제목·후보 소유권, 재시도 시각, 기제출 제외, 대표어 중복 제외 조건을 적용해 실제 제출 가능 재고를 계산한다. API 스냅샷에는 계정, 단계별 수량, 제출 이력, 일정, 작업기 상태만 허용 목록으로 복사하고 DB 접속 정보·경로·인증 정보는 보내지 않는다.

관제 자체 일정·지시는 별도 저장하며 결과를 기록한다. 원본 자동화의 설정과 연결하는 명령은 지원되는 필드만 바꾸고 기존 운영의 중복 제출 방지를 유지한다. 실데이터와 연결이 끊기면 마지막 관측 시각과 연결 끊김을 명확히 표시한다. 다른 사업은 미연결로 표시하며 사업 등록과 상태 관리가 가능하다.

심사·승인·공개 수량은 연결된 현재 고유 제작물 기준이다. 과거 제출 시도 횟수를 작품 수로 합산하지 않는다. 실행 잠금과 실제 제출 성공, 예상 심사일과 실제 승인도 구분한다.

현재 제출 실행 시각의 확정 예약은 제공되지 않는다. 수동 제출 계획, 자동 계정 확인·실패 재시도, 관제의 재확인 요청 예약을 구별한다. 다음 확인 시각을 다음 제출 시각으로 표시하지 않는다. 최신 배치의 제출 계획이 없으면 과거 배치의 계획을 되살리지 않는다.

월 수익은 별도 원장 `revenue_months`에 기록한다. 계정별 12개월을 조회·수정하고 미기록과 확정 0원을 구별한다. 현재 수익 자동 수집은 연결되지 않아 수동 확정 기록만 합산한다. 동시 수정은 revision으로 검사하고 같은 저장 요청을 다시 보내도 중복 처리하지 않는다.
